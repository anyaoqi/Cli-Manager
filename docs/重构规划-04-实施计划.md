# 重构规划 04 · 实施与验收计划

> 分支：`refactor/dotnet-wpf`。
> 只在用户确认本复核版后开发。是否提交 commit 由用户决定；计划不默认自动提交。

## 总体策略

采用“先验证最大风险，再做完整 UI”的顺序：
1. 先验证 .NET 构建/发布性能与无窗口启动链路。
2. 再正确建模 HKCR 合并视图和只读扫描。
3. 完成 CLI 启动与特殊路径矩阵。
4. 最后开放注册表写操作与完整 UI。
5. CLI 核心闭环通过后，再扩展其他 Windows 右键菜单位置。

预计：P0 核心约 6–8 人日；P1 通用静态菜单扩展约 2–4 人日。实际以 Phase 0 基线和验收结果调整，不把估算当承诺。

## Phase 0 · 架构尖峰与性能基线（0.5–1 日）

### 工作
1. 记录当前 Tauri 的干净构建、增量构建、发布、冷启动和体积，只作为重构前基线。
2. 安装 .NET 10 SDK，创建 `RightMenu.sln`、Core、App、Runner、Tests。
3. 锁定 WPF-UI、CommunityToolkit.Mvvm、xUnit、FluentAssertions 的稳定确切版本。
4. WPF 空窗口接系统主题；Runner 能在指定 `WorkingDirectory` 启动测试 CLI。
5. App 实现显式 `Main`：解析 `--launch` 时不创建主窗口；普通启动才加载 WPF Application。
6. 建初版 `build.ps1`：clean/build/test/publish 分步计时。

### 验收
- [ ] 修改一个 `.cs` 后增量构建 ≤3 秒。
- [ ] 干净 Debug 构建 ≤15 秒。
- [ ] 自包含 publish ≤45 秒；记录产物大小。
- [ ] 普通空窗口冷启动与 `--launch` broker 启动分别打点。
- [ ] Runner 在指定目录运行测试程序，测试程序写出的 cwd 与预期一致。
- [ ] 所有实测数字回填 01 §6；若 WPF 无法达到主要目标，先复盘再继续，不隐藏失败。

## Phase 1 · 注册表只读模型（1 日）

### 工作
1. 实现 `ContextLocation`、`StaticShellProvider` 与可注入的 registry accessor。
2. Phase A 只启用 `DirectoryBackground`。
3. 分别读取 HKCU/HKLM，保留值类型、未知值与子键元数据。
4. 计算有效、遮蔽、Explorer 可见、类型、可编辑能力与只读原因。
5. 展开 `@dll,-id` 间接显示名；解析图标但不阻塞首屏。
6. 建只读列表 UI：位置、搜索、分组、高级项开关、Inspector。

### 测试
- 单元测试全部使用内存 fake registry。
- 注册表集成测试使用随机测试 ProgID：`HKCU\Software\Classes\RightMenu.Test.<GUID>\shell`，不写真实 `Directory\Background\shell`，Drop/finally 双重清理。
- 用 fixture 覆盖：简单 command、LegacyDisable、Extended、ProgrammaticAccessOnly、AppliesTo、HideBasedOnVelocityId（本机 HKLM `cmd`/`WSL` 项实际在用，影响 Explorer 可见性计算）、DelegateExecute、子菜单、未知结构、HKCU/HKLM 同名遮蔽、旧版 `RightMenu.*` 遗留项（无 schema 元数据）。

### 验收
- [ ] 本机默认列表与 `HKCR\Directory\Background\shell` 人工核对；没有因黑名单丢项。
- [ ] 本机 HKLM 的 12 个用户/第三方项与 HKCU 的 3 项全部正确分类；OpenCode、Cursor 等简单项被标为“可迁移”，`RightMenu.codex` 被识别为旧版遗留项而非受管项。
- [ ] 默认折叠高级项，但展开后能看到隐藏/条件/复杂项。
- [ ] 复杂项明确只读；HKLM 简单项分类为“可迁移”（本阶段仅分类，迁移写操作在 Phase 3）。
- [ ] 首次扫描 ≤300ms；图标异步加载不阻塞列表。
- [ ] `dotnet test` 全绿，测试未改动用户真实菜单。

## Phase 2 · CLI 发现与安全启动链（1–1.5 日）

### 工作
1. 实现 `LaunchSpec`、`ManagedEntryService`、`TerminalDetector`、App broker 和 Runner。
2. 实现 Windows Terminal 与经典控制台兜底。
3. Runner 支持 `.exe`、`.cmd`、`.bat`；参数使用数组，工作目录不用 `cd` 字符串。
4. 实现 CLI 发现：进程/用户/系统 PATH、PATHEXT、App Paths、明确用户 bin、别名、多路径选择、手选。
5. 支持 Claude Code、Codex、Gemini、Kiro、Antigravity、OpenCode 的候选别名；不假装未安装工具已发现。
6. 建“测试启动”功能，但只有用户主动点击才运行真实 CLI。

### 自动化矩阵
测试目录至少包含：

```text
C:\RightMenuTests\normal
C:\RightMenuTests\含 中文 空格
C:\RightMenuTests\ampersand & dir
C:\RightMenuTests\paren (test)
C:\RightMenuTests\it's-valid
C:\RightMenuTests\semi;colon
```

`semi;colon` 专门验证 `wt.exe` 把 `;` 当作窗格分隔符的转义。

测试 CLI：
- 测试 `.exe` 将 cwd、argv、环境写入结果 JSON。
- 测试 `.cmd` / `.bat` 将 cwd 和参数写入文件。
- 参数覆盖空格、`&`、括号、`%`、`!`、单引号。

### 验收
- [ ] 每种目录 × 每种 CLI 类型均得到正确 cwd。
- [ ] 参数边界保持正确，不被 shell 拆分或注入。
- [ ] Windows Terminal 不存在时自动回退经典控制台。
- [ ] CLI 退出后保持/关闭行为符合设置。
- [ ] App broker 不显示管理窗口或闪现空白窗口。
- [ ] 本机已安装的目标 CLI 被发现；未发现项可手选。
- [ ] 右击到 Runner 进入可交互状态 ≤1 秒（不含 CLI 自身初始化）。

## Phase 3 · 目标键级 CRUD 与撤销（1–1.5 日）

### 工作
1. 先实现 `RegistrySnapshotStore`，再开放任何写操作。
2. 实现受管项 schema 和稳定 GUID 键名；`IsManaged` 判定基于 schema 元数据值而非键名前缀。
3. 实现 HKCU 简单项/受管项的新建、编辑、LegacyDisable 启停、删除、转换；旧版 `RightMenu.*` 遗留项的“升级为新受管项”。
4. 实现 02 §7.4 的 HKLM 简单项迁移：复制到 HKCU → 验证 → 一次显式 UAC 由提权 helper 删除原键；UAC 拒绝/删除失败的状态如实呈现。
5. 乐观并发检查：保存前比较扫描版本/目标键哈希。
6. 实现最近 50 次操作日志和目标键级撤销；冲突时不自动覆盖。
7. 显式 `.reg` 导出；导入延后到 P1，除非核心验收需要。

### 验收
- [ ] 新建 → 扫描 → 编辑 → 禁用 → 启用 → 删除 → 逐步撤销全部通过。
- [ ] HKLM 迁移：成功路径、UAC 拒绝、删除失败三种结果均有正确状态与快照；迁移后项可无提权编辑。
- [ ] 旧版 `RightMenu.codex` 式遗留项升级后符合新 schema，原命令备份在操作日志中。
- [ ] 编辑时未知值与未知子键不丢失。
- [ ] HKLM、DelegateExecute、子菜单和未知项写操作被 Core 拒绝，而不只是 UI 禁用。
- [ ] 两次并发变更能检测冲突，不覆盖第二方修改。
- [ ] 删除确认显示真实键路径；取消不产生操作记录。
- [ ] 受管项命令只包含稳定 App 路径、ContextLocation、entry ID 与目标参数，不包含脆弱的 `cd && CLI` 模板。
- [ ] portable 移动后能检测失效并修复受管项。

## Phase 4 · 完整 UI 与经典菜单（1–1.5 日）

### 工作
1. 按 03 完成主列表、位置选择、CLI 添加、Inspector、状态栏撤销、设置。
2. 完成键盘、焦点、屏幕阅读器、高对比度、DPI。
3. 经典菜单服务：精确快照、状态探测、开关、Windows 版本展示、Explorer 重启确认。
4. 失效路径诊断与修复。
5. UI 文案、错误提示和日志脱敏复核。

### 验收
- [ ] 03 §9 全部通过。
- [ ] 从“添加 CLI”到保存，已发现工具最多两步。
- [ ] Claude Code、Codex、Gemini、Kiro、Antigravity、OpenCode 中本机已安装的每一个均实际右击启动成功。
- [ ] 未安装工具通过手选测试程序完成同一流程。
- [ ] 经典菜单开/关在目标 Windows 版本实测并记录 DisplayVersion/Build；若失效，UI 明确标为不支持。
- [ ] Explorer 重启前明确提醒会关闭文件管理器窗口。
- [ ] `dotnet test`、Release build、人工 smoke test 全部通过。

## Phase 5 · 通用静态菜单扩展（P1，2–3 日）

严格按 provider 逐个开放，顺序：
1. Directory（文件夹对象）。
2. DesktopBackground。
3. Drive。
4. AllFiles 与 AllFilesystemObjects。
5. FileType（扩展名 → ProgID）。

每加入一个位置都必须：
- 定义正确目标参数语义（`%V` / `%1`）。
- 增加 HKCU/HKLM 合并与遮蔽 fixtures。
- 增加新建、编辑、启停、删除、撤销集成测试。
- 人工右击验证目标对象与工作目录/参数。
- 验收后才在 UI 位置列表中显示。

GUI/普通命令项在此阶段加入，但不能削弱 CLI 结构化 LaunchSpec 路径。

### 验收
- [ ] 每个启用位置均完成自动化与真实 Explorer 测试。
- [ ] FileType 显示扩展名与 ProgID 映射，不跨 ProgID 误删。
- [ ] 不复制五套 Reader/Writer；公共逻辑由 `StaticShellProvider` 复用。
- [ ] 所有位置切换复用同一主列表与 Inspector。

## Phase 6 · 高级盘点与发布（P2/发布，1 日起）

### 工作
1. 只读盘点常见 ContextMenuHandlers、DelegateExecute 与可识别现代扩展。
2. 展示 CLSID、来源、目标文件、发布者/签名（可得时）和缺失状态。
3. 不开放未经专门设计验证的 COM 删除。
4. 完成 Inno Setup 每用户安装包和 portable zip。
5. 安装到稳定路径；卸载时询问是否删除本工具创建的受管项，不碰用户原有项。
6. README 更新，四份规划补“实际与计划差异”。

### 发布验收
- [ ] 全新 Windows 用户账户可安装、启动、添加 CLI、右击运行、卸载。
- [ ] 无 .NET Desktop Runtime 的机器可运行自包含包。
- [ ] 安装包目标 ≤90MB；构建 ≤45 秒，超标有测量解释。
- [ ] 卸载默认保守，不删除非本工具创建项。
- [ ] 受管项在卸载前有清晰处理选择，卸载后不留下指向不存在 App 的命令。
- [ ] 无遥测、无项目/路径/环境数据网络传输。

## 开发纪律

1. 开发前读完 01–04；CLI 是第一优先级，但领域模型不得写死为只有 CLI/只有一个位置。
2. 不把旧 Rust 代码视为必须保留；它只提供行为样本。任何逻辑都可重写，但关键行为必须有测试覆盖。
3. 不在 WPF View/ViewModel 拼注册表路径或命令字符串。
4. 不先写 RegistryWriter；必须先有 snapshot/undo 与只读能力模型。
5. 自动化测试不写用户真实 `Directory\Background\shell`；真实键只用于经过确认的人工 E2E。
6. 不安装新依赖或改变打包器而不记录理由和确切版本。
7. 每个 Phase 都运行对应测试和性能测量；失败先修复或更新规划，不用“应该可用”代替证据。
8. 不自动创建 commit、推送或合并；除非用户明确要求。
