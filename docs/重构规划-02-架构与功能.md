# 重构规划 02 · 产品架构与功能规格

## 1. 产品模型

产品是 **CLI-first，而不是 CLI-only**：默认打开“文件夹空白处”，优先提供 Claude Code、Codex、Gemini、Kiro、Antigravity、OpenCode 等 CLI 的安全创建体验；底层用统一 `ContextLocation` 模型承载其他静态右键菜单位置。

首个交付位置：

```text
HKCU\Software\Classes\Directory\Background\shell
HKLM\Software\Classes\Directory\Background\shell
HKCR\Directory\Background\shell   # 上述两者的合并视图，不是独立存储区
```

后续 provider（在核心闭环通过后逐批启用）：

| ContextLocation | 注册表相对路径 | 场景 | 路径参数 |
|---|---|---|---|
| DirectoryBackground | `Directory\Background\shell` | 文件夹空白处 | `%V` |
| Directory | `Directory\shell` | 文件夹对象 | `%1` / `%V`，按动词类型 |
| DesktopBackground | `DesktopBackground\Shell` | 桌面空白处 | `%V` |
| Drive | `Drive\shell` | 磁盘 | `%1` |
| AllFiles | `*\shell` | 所有文件 | `%1` |
| AllFilesystemObjects | `AllFilesystemObjects\shell` | 文件与文件夹 | `%1` |
| FileType | `<ProgID>\shell` | 指定文件类型 | `%1` |

COM `shellex\ContextMenuHandlers`、`DelegateExecute`、打包应用和 Win11 `IExplorerCommand` 不套用静态动词 CRUD；后续仅做独立 provider 的只读盘点与诊断，除非有专门安全方案。

每个静态位置都完整枚举，不用黑名单把真实项藏起来，而是按能力分组：
- **受管启动项**：由本工具创建；CLI 可完整结构化编辑，GUI/普通命令使用受限模式。`IsManaged` 的判定依据是 `RightMenu.SchemaVersion` 等 schema 元数据值，**不是键名前缀**：本机已存在旧 Tauri 版创建的 `RightMenu.codex`（名称式键名、无元数据、旧式 `wt.exe -d "%V" cmd /k ...` 命令），它必须被识别为“旧版遗留项”并提供“升级为新受管项”入口，不能按新 schema 误解析或误判为受管。
- **现有简单命令**：已有 `command` 子键的 HKCU 项，可谨慎编辑/启停/删除。
- **可迁移的 HKLM 简单项**：结构与简单命令相同但位于 HKLM（用户用管理员 regedit 在 HKCR 下手工添加的项实际落在这里，本机占绝大多数）；提供“迁移到当前用户”后按普通可写项管理，见 §7.4。
- **只读/高级项**：`DelegateExecute`、子菜单、条件动词、`ProgrammaticAccessOnly` 等，以及系统/第三方安装器写入的复杂 HKLM 项；展示原因与原始信息，不做破坏性写入。
- **被遮蔽项**：HKCU 与 HKLM 同名时，展示有效来源和被遮蔽来源，避免把 HKCR 合并视图误当成单一键。

默认视图显示“有效且会在资源管理器中出现”的项；“显示高级项”打开后显示隐藏、条件、只读与被遮蔽项。扫描本身不丢数据。

`RightMenu.Core` 是唯一业务事实来源。UI 不拼注册表路径、不编译 shell 命令、不实现第二套预览逻辑。

## 3. 数据模型

### 3.1 扫描项

```csharp
public sealed record ShellVerb
{
    public required ContextLocation Location { get; init; }
    public required RegistryHiveSource Source { get; init; } // HKCU/HKLM
    public required string KeyName { get; init; }
    public required string DisplayName { get; init; }
    public string RawDisplayName { get; init; } = "";
    public string Command { get; init; } = "";
    public string IconSpec { get; init; } = "";
    public ShellVerbKind Kind { get; init; }                  // Command/Submenu/Delegate/Unknown
    public bool IsEnabled { get; init; }
    public bool IsExtended { get; init; }
    public bool IsExplorerVisible { get; init; }
    public bool IsEffective { get; init; }
    public bool IsShadowed { get; init; }
    public bool IsManaged { get; init; }                     // 依据 schema 元数据值，非键名前缀
    public bool IsLegacyManaged { get; init; }                // 旧版工具遗留项（如 RightMenu.codex）
    public EditCapability Capability { get; init; }           // Full/Simple/Migratable/ReadOnly
    public string? ReadOnlyReason { get; init; }
}
```

`Location + Source + KeyName` 是扫描实体主键。不能只用 KeyName，否则无法表达不同位置以及 HKCU/HKLM 同名遮蔽。

### 3.2 受管 CLI 启动规格

```csharp
public sealed record LaunchSpec
{
    public required string ExecutablePath { get; init; }
    public IReadOnlyList<string> Arguments { get; init; } = [];
    public TerminalKind Terminal { get; init; } = TerminalKind.Auto;
    public bool KeepOpenAfterExit { get; init; } = true;
}
```

参数按**数组**存储，不以一段 raw shell string 作为主数据，避免再次解析引号。

## 4. 受管项注册表协议

首个位置的新建项使用稳定 ID，而不是由显示名生成键名；后续位置复用同一 schema，只替换 `ContextLocation` 对应的父路径与目标占位符：

```text
HKCU\Software\Classes\Directory\Background\shell\RightMenu.<32位GUID>
  MUIVerb                 REG_SZ       在 Claude Code 中打开
  Icon                    REG_SZ       C:\Users\...\claude.exe,0
  RightMenu.Location      REG_SZ       DirectoryBackground
  RightMenu.SchemaVersion REG_DWORD    1
  RightMenu.Executable    REG_SZ       C:\Users\...\claude.exe
  RightMenu.Arguments     REG_MULTI_SZ [参数1, 参数2, ...]
  RightMenu.Terminal      REG_SZ       auto
  RightMenu.KeepOpen      REG_DWORD    1

...\command
  (Default) REG_SZ "<稳定安装路径>\RightMenu.App.exe" --launch "DirectoryBackground" "RightMenu.<GUID>" "%V"
```

优点：
- 改显示名不需要重命名注册表键。
- 参数保持结构化，不把 CLI 路径与参数塞进多层 shell 引号。
- 注册表仍是启动项唯一事实来源，不依赖另一个易漂移的 JSON 菜单数据库。
- 更新/修复时可以重写 App 路径；portable 目录移动后，应用启动时可检测并提供“修复受管项”。

## 5. 启动链路

```text
Explorer
  → RightMenu.App.exe --launch <location> <entry-id> <target-path>
      （显式 Main 在创建 WPF Application/窗口前识别参数，走无窗口模式）
  → 读取并验证 LaunchSpec
  → 选择终端
      Windows Terminal: wt.exe -d <cwd> RightMenu.Runner.exe --location <location> --entry <id> --cwd <cwd>
      兜底: 直接以新控制台启动 RightMenu.Runner.exe
  → Runner 读取 LaunchSpec，以 cwd 为 WorkingDirectory 启动 CLI 并等待
```

关键原则：
1. **不使用 `cd /d "%V" && ...` 作为受管项启动机制。** 工作目录通过 `ProcessStartInfo.WorkingDirectory` 和 Windows Terminal 的结构化参数传递。
2. 所有进程参数尽量用 `ProcessStartInfo.ArgumentList`，不手拼一整条命令。
3. `.exe` 直接启动；`.cmd/.bat` 由 Runner 通过一个集中、经过特殊字符测试的 `CmdScriptLauncher` 调用；不允许 UI 自己拼接。
4. Runner 继承终端控制台，等待 CLI 退出；`KeepOpenAfterExit=true` 时显示退出码并等待按键，避免标签页瞬间关闭。
5. 目标目录必须是存在的绝对路径；CLI 路径必须是存在的文件。错误写入本地日志并在可能时给出可读提示。

现有手工项保留其 raw command。编辑时提供：
- “简单编辑”：显示名、图标、原始命令。
- “转换为受管 CLI”：选择可执行文件和终端，生成上述协议。

## 6. CLI 发现

内置目录只提供**候选名称与别名**，不硬编码某个用户的安装位置：

| 工具 | 候选别名（实现时以实机核对为准） |
|---|---|
| Claude Code | `claude` |
| Codex | `codex` |
| Gemini CLI | `gemini` |
| Kiro | `kiro`, `kiro-cli` |
| Antigravity | `antigravity` |
| OpenCode | `opencode` |

发现流程：
1. 合并当前进程 PATH、`HKCU\Environment\Path`、系统环境 PATH，展开环境变量并去重。
2. 按 PATHEXT 搜索 `.exe/.com/.cmd/.bat`；兼容 Explorer 尚未刷新环境变量的情况。
3. 查询 `App Paths` 与少量明确的用户级 CLI 目录（如 `%USERPROFILE%\.local\bin`、npm/pnpm/bun 全局 bin）。
4. 对候选执行文件做存在性验证，显示完整路径、扩展名与发现来源。
5. 同名多路径时让用户选择，不擅自猜“正确版本”。
6. 永远提供“浏览选择”和“手动输入”；未发现不是错误。

不在扫描阶段执行未知 CLI，也不把项目代码、路径或环境变量发送到网络。

## 7. 注册表 CRUD 语义

### 7.1 可写范围
- Phase A 新建只写 HKCU `Directory\Background\shell`；Phase B 按 provider 白名单逐个开放其他静态 `shell` 位置。
- 编辑/启停/删除只处理已启用 provider 下的 HKCU 简单命令项与受管项。
- HKLM 简单项不就地编辑，通过 §7.4 迁移后管理；其余 HKLM 项、DelegateExecute、子菜单、COM handler、未知结构：只读。
- 不通过 HKCU 遮蔽技巧修改 HKLM 项，避免产生难以理解的合并结果。
- FileType provider 必须显示具体 ProgID 与文件扩展名映射，禁止“一键删除所有同名动词”这类跨 ProgID 操作。

### 7.2 保守更新
- 编辑简单项只改用户明确提交的 `MUIVerb`/默认显示名、`Icon`、`command` 默认值。
- 未识别值与子键原样保留。
- 删除前显示来源、完整键路径和影响；默认焦点在取消。
- 启停使用 `LegacyDisable`，恢复时只移除本次写入的值。

### 7.3 操作日志与撤销

不再“每次 `reg export` 整棵挂载点，再 import 整棵树”。那会把备份后其他程序或用户写入的无关变更一起覆盖。

改为目标键级事务快照：
- 每次变更前递归读取**目标动词键**的值、类型、子键；创建操作记录“原先不存在”。
- 保存为 `%LOCALAPPDATA%\RightMenu\operations\<timestamp>-<id>.json`，包含操作类型、目标路径、before、after、应用版本。
- 撤销只恢复该目标键；若当前状态与记录的 after 不一致，先提示冲突，不静默覆盖。
- 保留最近 50 次操作。
- 用户主动“导出注册表”时才调用 `reg.exe export` 生成 `.reg`；导入属于高级操作，必须先预览目标路径并再次确认。

经典菜单开关也对它自己的 CLSID 键做精确快照，不备份整个 `Classes`。

### 7.4 HKLM 简单项迁移（“迁移到当前用户”）

用户以管理员在 regedit 的 HKCR 下手工添加的项实际写入 HKLM（本机实测：OpenCode、Cursor、Cmder 等 12 项在 HKLM，HKCU 仅 3 项）。为满足“管理已有项”的核心需求：

1. 仅适用于**结构简单**的 HKLM 项：普通 `command` 动词、无 DelegateExecute/子菜单/未知子键；复杂项仍为只读。
2. 迁移流程：先完整复制到 HKCU 同名键（无需提权）→ 验证复制结果与源一致 → 弹出**一次显式 UAC**，由提权 helper 仅执行“删除该 HKLM 原键”单一操作。
3. UAC 被拒绝或删除失败时：HKCU 副本保留并生效（同名遮蔽），UI 如实显示“已迁移，原 HKLM 项仍存在且被遮蔽”，提供重试删除、不伪装迁移完成。
4. 迁移前对 HKLM 原键与 HKCU 目标键均做 §7.3 快照；撤销时恢复 HKCU 副本删除，HKLM 原键的恢复需再次提权并明确确认。
5. 迁移后的 HKCU 项按“现有简单命令”管理，后续增删改查与启停全部无需提权，并可“转换为受管 CLI”。
6. 提权 helper 不常驻、不接受任意路径：只删除白名单 `ContextLocation` 下、由主进程快照验证过的单个动词键。

## 8. 经典菜单开关

目标键：

```text
HKCU\Software\Classes\CLSID\{86ca1aa0-34aa-4e8b-a509-50c905bae2a2}\InprocServer32
```

空默认值通常用于恢复经典菜单；关闭时只恢复本工具变更前的精确状态，而不是无条件删除整个 CLSID 键。

这是非官方、可能随 Windows 更新失效的兼容 hack：
- UI 标记“实验性”。
- 显示当前 Windows DisplayVersion / Build。
- 开启或关闭后提示需要重启 Explorer，并提供明确确认；不在后台自动杀 Explorer。
- Phase 4 必须在目标系统实测；无效时明确显示“不受当前系统版本支持”，不承诺所有 Win11 版本有效。

## 9. 功能优先级

### P0：CLI 核心闭环（DirectoryBackground）
- 完整扫描 `Directory\Background\shell`，正确表达 HKCU/HKLM 合并、遮蔽、类型与可写性。
- 搜索与分组。
- 从发现结果或手选路径创建受管 CLI。
- 受管 CLI 查看、编辑、启停、删除。
- 现有 HKCU 简单命令项查看、编辑、启停、删除、转换。
- HKLM 用户简单项“迁移到当前用户”（§7.4）；这是 P0 必须项，因为用户现有 CLI 菜单主要在 HKLM。
- 旧版 `RightMenu.*` 遗留项识别与“升级为新受管项”。
- 目标键级操作日志、撤销。
- Windows Terminal + 经典控制台兜底。
- 经典菜单实验性开关。

### P1：扩展为通用静态右键菜单管理器
- 通过同一 `StaticShellProvider` 依次开放 Directory、DesktopBackground、Drive。
- 再开放 AllFiles、AllFilesystemObjects 与 FileType；每一类单独验收目标参数 `%V`/`%1`。
- 支持普通 GUI/命令受管项；CLI 仍保留更安全的结构化启动体验。
- 批量添加多个 CLI。
- 显式 `.reg` 导出/导入。
- 失效路径诊断与一键修复。
- 受管项安装路径修复。
- 主题偏好、默认终端、保持窗口偏好。

### P2：高级盘点
- 只读枚举常见 `ContextMenuHandlers`、DelegateExecute 和现代扩展来源。
- 展示 CLSID、签名/发布者（可得时）、注册位置与目标文件是否存在。
- 未建立专门回滚与兼容测试前，不开放删除 COM/现代扩展。

## 10. 验收矩阵

必须自动化或人工覆盖：

| 维度 | 用例 |
|---|---|
| 目录 | 普通路径、空格、中文、`&`、`( )`、单引号、`;`（wt.exe 的窗格分隔符，需验证转义）、深层路径 |
| CLI 类型 | `.exe`、`.cmd`、`.bat` |
| CLI 参数 | 无参数、多个参数、参数含空格和 `&` |
| 终端 | Windows Terminal 已安装 / 不存在时经典控制台兜底 |
| 图标 | `.exe,索引` 正常提取；`.cmd`/`.bat` 无图标资源时回退到终端/默认图标，不显示破图（本机已存在 `codex.cmd,0` 这类 IconSpec） |
| 注册表 | HKCU、HKLM 只读/可迁移、同名遮蔽、LegacyDisable、Extended、HideBasedOnVelocityId（本机 `cmd`/`WSL` 项实际在用）、条件项、DelegateExecute、子菜单 |
| 事务 | 新建/编辑/启停/删除后撤销；HKLM 迁移成功/UAC 拒绝/删除失败；并发变化冲突不覆盖 |
| 安装 | 稳定安装路径、portable 移动后的检测与修复 |
| OS | 当前 Windows 版本；经典菜单开关开/关/不支持 |

端到端最低要求：Claude Code、Codex、Gemini、Kiro、Antigravity、OpenCode 中，本机已安装的每一个都要实际右击启动；未安装项验证发现失败后可手选路径。
