# 重构规划 01 · 需求边界与技术栈决策

> 分支：`refactor/dotnet-wpf`
> 状态：规划复核版，待用户确认后开发
> 决策原则：**只根据需求选择，不把现有实现、迁移成本或既有语言当作约束。**

## 1. 核心需求

本项目是一个 **CLI-first 的 Windows 右键菜单管理器**。最先、最深地解决文件夹空白处启动 CLI；领域模型和后续路线允许扩展到其他常见 Windows 右键菜单。

必须解决：
1. 在资源管理器的文件夹空白处右击，可在该目录直接交互启动 Claude Code、Codex、Gemini、Kiro、Antigravity、OpenCode 等 CLI。
2. 查看并安全管理 `HKEY_CLASSES_ROOT\Directory\Background\shell` 对应的静态菜单项：新增、查看、编辑、启用/禁用、删除。
3. 能识别并管理用户已经手工添加的项目，不破坏无关菜单。**实机核查事实**：用户以管理员在注册表编辑器 `HKCR` 下手工添加的项实际存储在 `HKLM\Software\Classes`（本机 12 项，含 OpenCode、Cursor、Cmder 等），HKCU 仅 3 项。因此“管理已有项”必须覆盖用户自己的 HKLM 简单项，否则工具对现有菜单的管理覆盖率不足两成。
4. 开发构建、发布打包和应用启动都要快。
5. UI 简洁、清晰、像成熟 Windows 工具，不像网页模板或 AI 批量生成界面。
6. 提供用户已确认的“恢复经典右键菜单”开关；它是实验性、可逆的附加功能。

成功标准不是“注册表里出现了一个键”，而是：在包含空格、中文、`&`、括号、单引号的目录里右击后，`.exe`、`.cmd`、`.bat` 类型的 CLI 都能在正确工作目录中交互运行。

## 2. 范围边界

### 产品愿景

产品以 CLI 为最常用场景，但不把领域模型锁死为 CLI 专用。最终可覆盖 Windows 常见右键菜单来源：
- 静态 `shell` 动词：文件夹空白、文件夹、桌面、磁盘、所有文件、所有文件系统对象及特定文件类型。
- COM / `ContextMenuHandlers` / `IExplorerCommand`：后续提供来源与状态盘点；只有能证明安全、可逆时才开放修改。

“Windows 所有右键菜单”不能被理解为所有项目都能统一 CRUD：部分菜单由 COM、打包应用或运行时条件动态生成，注册表结构和权限不同。产品必须如实显示支持级别，不伪装成全能清理器。

### MVP（第一条可交付闭环）
- 完整管理 `Directory\Background\shell`（文件夹空白处），优先服务 CLI。
- 完整显示该位置的静态 `shell` 动词，标明来源、类型与可编辑性。
- 新建“受管启动项”，CLI 使用专用安全启动模型；普通 GUI/命令项可使用受限高级模式。
- Windows Terminal 优先，经典控制台兜底。
- HKCU 写操作；HKLM 不就地编辑，但对 HKLM 用户简单命令项提供“迁移到当前用户”（复制到 HKCU 后经一次显式 UAC 删除原键，迁移后按普通可写项管理）。
- 目标键级撤销、显式 `.reg` 导出（导入放到 P1）、经典菜单实验性开关。

### 后续扩展（核心闭环通过后）
1. `Directory\shell`、`DesktopBackground\Shell`、`Drive\shell`。
2. `*\shell`、`AllFilesystemObjects\shell` 与常见文件类型 ProgID 的静态动词。
3. COM Shell 扩展与 Win11 现代扩展的只读盘点、定位与诊断。

### 明确不承诺
- 常驻提权或在 HKLM 内就地编辑；唯一提权场景是用户显式确认的“迁移到当前用户”删除原键。
- 在不了解 COM 扩展协议时直接删除 DLL/CLSID。
- 云同步、遥测、自动更新、伪造注册表“排序”。

扩展通过 `ContextLocation`/provider 模型实现，不能为后续位置复制一套扫描与写入代码。

## 3. 技术栈结论

**采用 .NET 10 LTS + WPF + WPF-UI + CommunityToolkit.Mvvm。**

解决方案包含：
- `RightMenu.App`：WPF 管理界面，也承担 Explorer 调用时的无窗口 broker 模式。
- `RightMenu.Runner`：轻量 console helper，在目标终端内直接运行 CLI。
- `RightMenu.Core`：注册表模型、CLI 发现、启动编译、备份与恢复。
- `RightMenu.Core.Tests`：无 UI 的单元与集成测试。

### 为什么它最适合本需求

1. **Windows-only 是确定前提。** WPF 不为跨平台抽象付费，`Microsoft.Win32.Registry`、`ProcessStartInfo.ArgumentList`、P/Invoke、系统主题与文件图标都能直接使用。
2. **开发与打包快。** C# 增量构建通常是秒级；没有 Cargo 大规模链接，也没有 Node/Vite 前端链。发布就是 `dotnet publish`，可再由安装脚本打成每用户安装包。
3. **启动路径短。** 没有 WebView2 初始化和前后端 IPC；管理窗口是本地控件，右键启动时可走无窗口 broker，不创建 WPF 主窗口。
4. **原生观感成本低。** WPF-UI 提供 Fluent 窗口、主题、控件和对话框；设计精力用于信息层次与交互，而不是重新实现按钮、开关、焦点管理和无障碍语义。
5. **命令编译只有一份。** UI 预览和真实写入都调用同一个 C# `LaunchSpecCompiler`，不再维护 TS/Rust 两套字符串逻辑。
6. 用户已确认约 70MB 可接受，因此 WPF 自包含发布体积不是阻断项。

## 4. 候选方案复核

| 方案 | 构建/打包 | Windows API | UI 质感 | 发布体积 | 结论 |
|---|---|---|---|---|---|
| **.NET 10 + WPF** | 秒级增量；发布简单 | 一等支持 | WPF-UI 提供成熟 Fluent 基础 | 约 60–100MB 自包含 | **最匹配** |
| WinUI 3 | 构建较快 | 一等支持 | 最接近原生 Win11 | 中等 | 打包与部署复杂度高于本项目收益 |
| Tauri v2 + Svelte | UI HMR 快；Rust 改动和发布链接较慢 | Rust 可做但绑定繁琐 | 可高度定制，但需自建控件与无障碍 | 小 | 跨平台与小体积不是核心，增加两套语言和 IPC |
| Wails + Go | Go 构建快 | 注册表可用，Shell API 需 syscall | Web UI | 小 | Wails v3 稳定性与 Win32 细节不如 .NET |
| Electron + React | UI 开发快，包大 | 需原生模块或外部进程 | Web UI | 最大 | 对注册表/Shell 工具不合适 |
| Avalonia | 构建快 | 可用 .NET API | 非原生绘制 | 中等 | 跨平台价值在本需求中无用 |

### 为什么不用 Tauri

不是因为 Rust 做不到，而是它对本需求没有净收益：
- 项目只支持 Windows，不需要 Tauri 的跨平台外壳。
- 小体积不再是决定因素；用户已接受约 70MB。
- 需求强调编译、打包、启动和 UI 打磨；WPF 省去 Rust 链接、WebView2、前后端 IPC、Web 控件无障碍与自定义标题栏维护。
- 注册表、进程参数、文件图标、系统主题都属于 .NET/WPF 的优势区。

旧 Rust 代码可以作为行为参考和测试样本，但不作为架构约束；正确逻辑可移植，错误或复杂逻辑直接重写。

### 为什么不用 Go / Node / Vite / React / Tailwind

- Go 的构建速度很好，但本项目大量使用 Windows Shell/注册表语义，C# 的标准库、P/Invoke 生态和桌面 UI 更完整；Wails 仍会引入 WebView 与前后端桥接。
- Node 对注册表与 Shell API 不是一等支持，最终仍需原生扩展或调用 `reg.exe`，增加编码、错误处理和部署复杂度。
- Vite/React/Tailwind 只解决 Web UI，不解决桌面外壳、注册表和进程启动。选它们意味着再引入 Electron/Tauri/Wails。
- Tailwind/shadcn 风格很容易产生同质化“AI 模板感”；本项目更适合使用 Windows Fluent 控件与少量定制 token。

## 5. 依赖与发布策略

| 层 | 选择 | 约束 |
|---|---|---|
| Runtime | .NET 10 LTS / `net10.0-windows` | SDK 在开发机安装；发布自包含 |
| UI | WPF + WPF-UI | 开发开始时锁定最新稳定确切版本，不使用版本区间 |
| MVVM | CommunityToolkit.Mvvm | 只使用源生成属性/命令与消息能力 |
| Registry/JSON/Process | .NET BCL | 不引入第三方注册表或命令行解析库 |
| 测试 | xUnit + FluentAssertions | 锁定确切版本 |
| 安装 | `dotnet publish` 自包含文件夹 + Inno Setup 每用户安装包 | 安装到稳定路径，无需管理员；同时产出 portable zip |

发布不启用 trimming（WPF 不适合激进裁剪），默认不启用 ReadyToRun（优先发布速度和体积）；只有冷启动实测不达标时才评估 ReadyToRun。

## 6. 性能目标

Phase 0 已测基线（2026-07-28，Debug 构建、本机实测）。旧 Tauri 基线无法补测：用户在重构前已删除全部业务代码。

| 指标 | 目标 | Phase 0 实测 |
|---|---|---|
| 修改一个 `.cs` 后增量构建 | ≤ 3 秒 | **1.6s** ✅ |
| 干净 Debug 构建 | ≤ 15 秒 | **1.8s** ✅（首次含 NuGet 下载 57s，不计入） |
| 自包含发布 + 安装包 | ≤ 45 秒 | **42.5s**（App 40.4s + Runner 2.1s，首次含 win-x64 运行时包还原；安装包打包 Phase 6 补测） |
| 冷启动到列表可操作 | ≤ 800 毫秒 | 空窗口 Loaded **639ms**（Debug；列表实现后 Phase 1/4 复测） |
| 右键点击到终端可交互 | ≤ 1 秒（不含 CLI 自身启动） | broker 进程内 **63–117ms**，含进程创建全程 **128ms**（启动链 Phase 2 实现后复测端到端） |
| 首次扫描 `Directory\Background\shell` | ≤ 300 毫秒 | Phase 1 实测 |
| 安装包 | 目标 ≤ 90MB；若超过需解释构成 | 未压缩自包含发布目录 146MB（App+Runner 共享目录）；Inno Setup 压缩后 Phase 6 实测 |
| 空闲内存 | 目标 ≤ 120MB | Phase 4 实测 |

性能不达标先用测量定位，不提前添加缓存、AOT 或复杂构建器。

环境备注：本机默认 `DOTNET_ROOT`/PATH 指向 `C:\Users\admin\Tools\dotnet`（仅 8.x），.NET 10 在 `C:\Program Files\dotnet`；`build.ps1` 会在会话内自动覆盖。解决方案文件为 .NET 10 默认的 `RightMenu.slnx` 格式。

## 7. 决策稳定性

只有以下需求变化才重新选型：
- 明确要求支持 macOS/Linux；
- 明确要求安装包小于 15MB；
- 明确要求 Win11 一级菜单 `IExplorerCommand`/MSIX 深度集成。

否则不再因“旧代码已存在”或“某语言更熟”改变架构。
